01 / The review

The foundations are good.
The handoffs need work.

BoltPage already has a restrained document surface, live preview, a workspace, and serious editing tools. The next useful redesign connects those capabilities around the document.

Basis: current viewer/editor HTML, CSS and JavaScript; native menu and window code; project briefing; repository screenshot. This is a source-based interaction review and visual inspection, not a native-app usability study. No measured speed improvement is claimed.

Preserve what is working: fast local rendering, CodeMirror, on-type preview, bidirectional scroll sync, docked Find, themes, native menus, session restore, and optional multi-window use. The older redesign proposal describes changes already present in the current source; it is not the baseline for this review.

01

One place for a document

Read, edit, and compare in the same window. Keep the filename, navigation, and save state stable through each transition.

02

Find the right thing

Give file switching, folder search, and document Find explicit scopes. A search result should land at its specific passage.

03

Make state actionable

A saving error or external change needs a recovery action next to the explanation. A small status badge alone is insufficient.

Findings, with evidence

“Observed” is supported by the source. “Impact” is a design assessment, except the explicit overwrite risk. Priorities reflect task disruption, not visual preference.

Scope of confidence

Separate editor windows, sidebar exclusivity, search click-through behavior, shortcut wiring, toolbar structure, and save logic are confirmed in source. Their usability cost is an informed hypothesis. Native hit testing, screen-reader output, actual window positioning, PDF rendering, and Windows behavior still need hands-on testing. I do not know whether the current window arrangement is faster for your dual-monitor workflow.

The recommendation is therefore an integrated default with an optional detached editor. This preserves a useful existing workflow while making quick corrections simpler. No tabs, accounts, collaboration, AI controls, or new infrastructure are proposed.

02 / Design decisions

A document first.
A workspace when needed.

The redesign is a change in structure and interaction priority. Color and typography support that structure.

A stable document shell

The title and path identify the file. Read / Edit / Split is the main view control. Find, Appearance, information, and Export occupy the same positions in every mode. Open, New, folder search, and commands belong with navigation.

Read is the first-open default. Remember the last mode per document after deliberate selection. Restore scroll anchor, cursor, selection, search, and dirty state when changing modes. Keep separate document windows and “Detach editor” in the native Window menu.

Two levels of navigation

Files answer “which document?” The outline answers “where inside it?” Stack them in a single sidebar. Search temporarily occupies that sidebar and preserves its query when a result opens.

With no folder, show the current outline and recent files. For a document with no headings, show a useful empty state. On a narrow window, reveal navigation as a dismissible drawer; never steal the reading width permanently.

Visual language

Quiet, layered surfaces

A paper document, a slightly darker navigation surface, and a restrained green selection. Amber signals attention; text and an action explain why. Accent hue is a proposal, not an efficiency claim.

Aa

Reading and operating

A system sans for controls; Iowan / Palatino / Georgia for prose; system monospace for source. Retain Serif, Sans, and Mono choices. Use local fonts and existing vendored assets.

34 / 44

Comfortable targets

Use 34px controls in desktop chrome, with 44px as the touch-friendly implementation target. Use visible focus rings, text labels for unfamiliar icons, and a consistent spacing scale.

Accessibility is part of efficiency

Use native buttons and inputs, explicit accessible names, visible selected states, logical tab order, focus containment for dialogs, Escape to dismiss, and focus return to the invoking control. Results and saving changes need restrained announcements. Do not rely on color alone.

The prototype uses native browser dialogs and a 3px focus outline. Production needs testing with VoiceOver and Narrator, enlarged text, keyboard-only navigation, and high-contrast settings.

Target at least 4.5:1 contrast for normal text, 3:1 for large text and meaningful UI boundaries; verify each theme. The demo is not a declaration of full WCAG conformance.

Reference: W3C WCAG 2.2 for keyboard, focus, contrast, and status messages; target size guidance specifies a 24 × 24 CSS pixel minimum with exceptions. The proposed larger controls are a design choice.

Preserve the product boundary. Keep Rust rendering and sanitization, file grants, strict CSP, offline dependencies, macOS/Windows support, and the existing no-Linux/no-wiki-link scope. This single-file browser prototype does not replace those production components.

Make the common path clear; keep the advanced path available.
03 / Implementation

Improve the flow.
Protect the engine.

Deliver this in bounded stages. The unified editor is a structural change; it deserves an explicit implementation decision after you have tried the proposal.

1

Clarify controls and recovery

Fix the Edit shortcut hint, label the launcher and search scopes, bring PDF into the export surface, expose persistent save failure actions, and make appearance/inspector entry points consistent. Review the conflict policy first; pausing autosave changes deliberate behavior.

Boundary: viewer/editor toolbar, menus, status and conflict handling; preserve current window architecture.

Acceptance: every displayed shortcut invokes its named action; all save failure states keep the buffer and offer recovery; simulated external writes cannot destroy either version under an approved policy.

2

Connect file and passage navigation

Separate the file list from the current outline. Search results carry the hit location into preview/source and retain query and selected result. Add visible indexing, empty, truncated, permission, and error states. Preserve fuzzy switching and native recents.

Boundary: workspace sidebar and search-to-document navigation; reuse existing search/index services.

Acceptance: selecting the third repeated match opens the third passage, not the first; switching back preserves search context; no-folder search explains how to open a folder.

3

Bring the editor into the document window

Mount the existing CodeMirror editor beside the preview. Give the document one buffer/save owner shared by view modes. Retain detached editing as an explicit option. Preserve anchored preview patching, scroll sync, formatting, folding, Vim, image paste, and session restoration.

Boundary: shared document state, editor lifecycle, event routing, window/close handling, and preference scoping. This is the main refactor, not a CSS-only change.

Acceptance: 20 Read/Edit/Split transitions preserve content, undo history, cursor, and position; no duplicate watchers or autosave races; closing either attached or detached views cannot discard unsaved content.

4

Validate with real tasks on both platforms

Compare the current build and the redesign with the same files and tasks. Alternate test order to reduce learning bias. Include people who favor a single window and people who use two monitors.

Measure: completion time, navigation/window actions, wrong-file edits, recovery success, and stated confidence. Ship an integrated default only if quick-edit tasks improve without impairing reading or detached workflows.

Task script for a usability session

  1. Open a Markdown file from the desktop. Find its third section and correct one word while keeping your place.
  2. Open a folder, search a phrase that repeats, and navigate to the second result in another file.
  3. Export the edited document as HTML and PDF. Explain what each includes.
  4. Edit in another application while BoltPage has unsaved changes. Recover both versions without guessing which is safe.
  5. Repeat navigation and appearance changes with keyboard only and at enlarged text size.
  6. Open JSON, YAML, TXT, and PDF; explain which controls apply. Test read-only and missing files.
